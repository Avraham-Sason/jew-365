# AGENTS.md

## Purpose

- Own non-React app logic and native-facing service wrappers.

## Ownership

- [ZmanimService.ts](ZmanimService.ts) owns kosher-zmanim calculations and caching, the per-location candle-lighting minutes (`candleLightingMinutes()`, `isJerusalem()`, which reads `cityId === 'jerusalem'`, never a display name) and the Shabbat / Yom Tov exit margin (`HOLY_BLOCK_EXIT_MIN`, `holyBlockExit(zmanim)`: ten minutes after tzeit, the user's call on 2026-10-10). They live here, below every caller, so no service imports the mitzvah registry and no require cycle forms.
- [HebcalService.ts](HebcalService.ts) owns Hebrew calendar, holidays, Shabbat, chol hamoed, holy blocks, Daf Yomi, and Omer logic (`getHolidays()` and `getParasha()` take a `CalendarLocale`: `he` with vowel points, `en`, or `he-x-NoNikud`, the form the notices and the weekly report print; `getHolidays()` takes a fourth argument `{ cholHamoed?, erev? }` that adds chol hamoed days, Hoshana Raba included, and erev days to the list, off by default so the schedule and the reader keep their lists, and the weekly report's next week turns both on), and `nightfall(zmanim, loc)`: when the night after a day opens, its tzeit, or the block's exit on the last day of a holy block, which every night window of that day (maariv, the Omer, havdalah, a tevila) takes as its start.
- [LocationService.ts](LocationService.ts) owns location access wrappers. A GPS fix within 25 km of a `CITIES` entry borrows that city's `cityId`, name, zone, `inIsrael`, elevation and `candleLightingMinutes` and keeps its own latitude and longitude; a far fix carries none of them.
- [StorageService.ts](StorageService.ts) owns MMKV-backed storage helpers.
- [TaharahStorage.ts](TaharahStorage.ts) owns the encrypted MMKV instance behind [../stores/useTaharahStore.ts](../stores/useTaharahStore.ts), its key in the secure store, and `clearTaharahStorage()`.
- [biometricLock.ts](biometricLock.ts) owns the taharah biometric lock: `lockStatusFor()`, `biometricsAvailable()`, `authenticate()` (one shared prompt at a time, `isAuthenticating()`), and the module-level session (`isSessionUnlocked()`, `markUnlocked()`, `relock()`) used by [../components/TaharahLock.tsx](../components/TaharahLock.tsx) and [../app/taharah/_layout.tsx](../app/taharah/_layout.tsx). It never touches the native module on web. `expo-local-authentication` is a native dependency, so the lock ships with a build. Its suite is [__tests__/biometricLock.test.ts](__tests__/biometricLock.test.ts); the root mock [expo-local-authentication.js](../../__mocks__/expo-local-authentication.js) stands in for the module (`__set`, `__reset`).
- [NotificationScheduler.ts](NotificationScheduler.ts) is the notification facade: the `NotificationScheduler` object (lock, rebuild, cancel), suppression and mark-done from a notification, the update notice, permission state, the handlers' subscriptions and both background tasks. The schedule itself is built in [notifications/](notifications/AGENTS.md): constants and id helpers, the store snapshot, the pure planners (mitzvot, holy-block notice, hilulot, Rosh Chodesh, check-in, weekly report, taharah reminders built from [../utils/taharah/tasks.ts](../utils/taharah/tasks.ts)) and the one adapter over expo-notifications.
- [NotificationScheduler.web.ts](NotificationScheduler.web.ts) owns web shim parity for scheduler exports. `buildTriggerTime` and `nextReminderAt` are the two pure planner functions it re-exports as they are, so the shim holds no second copy of the trigger rule.
- [notificationResponseHandler.ts](notificationResponseHandler.ts) owns notification tap/action responses.
- [SiddurService.ts](SiddurService.ts) owns loading a nusach text asset (`loadSiddurText()`) and a Chok LeYisrael parasha asset (`loadChokParasha()`) from disk (fetch on web), each read once and cached; a failed read is forgotten so the next open retries. Suite: [__tests__/SiddurService.test.ts](__tests__/SiddurService.test.ts).
- [CompletionService.ts](CompletionService.ts) and [AppResetService.ts](AppResetService.ts) own completion/reset service behavior. `CompletionService` only forwards to the completions store: every scheduler call (cancel, settle, rebuild) is queued by the store action itself, so the service adds none of its own.
- [errors.ts](errors.ts) owns the error channel: `reportError(scope, error)` (scopes `schedule`, `completion`, `reset`, `storage`) keeps the latest failure as a `LastError` under the MMKV key `errors:last`, serves it through `getLastError()`, `subscribeToLastError()` and `useLastError()` (a `useSyncExternalStore` over a cached read; a subscriber also listens to `AppState` and on `'active'` re-reads MMKV through `refreshLastError()`, because a headless JS context writes `errors:last` where this context's cache never looks, notifying only when the stored value differs), warns in development and hands the error to [crashReporting.ts](crashReporting.ts); `clearLastError()` drops it. It never throws into the code it reports on. The scheduler facade (store-driven `rebuild()` and `cancelAll()`, the permission sync, the foreground refresh and the daily task), `AppResetService` (scope `reset`, and it clears the last error before it resets), the onboarding ready and location steps, the settings notification toggle and the permission syncs on home and Settings report the failures they used to swallow, and a `rebuild()` that completes (so `rebuildForNewDay()` too) clears a `schedule` error; cosmetic catches (haptics, Linking, keep-awake) and the planners' own guards in [notifications/plan.ts](notifications/plan.ts) stay as they are. Home shows a banner for a `schedule` or `reset` error. The reporter is [crashReporting.native.ts](crashReporting.native.ts) on a device and the no-op [crashReporting.ts](crashReporting.ts) on web and in Jest. Suites: [__tests__/errors.test.ts](__tests__/errors.test.ts) and [__tests__/errors.integration.test.ts](__tests__/errors.integration.test.ts).
- [crashReporting.native.ts](crashReporting.native.ts) owns Sentry on a device. `Sentry.init` runs when the module loads, and [../../index.js](../../index.js) imports it before anything else, so a headless launch is covered too. Reporting is on only off web, outside development and with `EXPO_PUBLIC_SENTRY_DSN` set (`crashReportingEnabled`); otherwise `captureException()` does nothing. It sends no PII (`sendDefaultPii: false`, a zeroed `ip_address`) and no traces, and drops `touch` and `console` breadcrumbs, so what a user tapped or logged, taharah screens included, never leaves the device. Every event carries the `updateId`, `channel` and `runtimeVersion` tags, and `captureException(error, { scope })` adds the scope as a tag: [errors.ts](errors.ts) reports through it, and the exported `ErrorBoundary` in [../app/_layout.tsx](../app/_layout.tsx) reports with scope `render` (that layout's default export is wrapped in `Sentry.wrap`). The SDK is native, so it ships only in a build.
- [crashReporting.ts](crashReporting.ts) is the same two exports, `crashReportingEnabled` (always false) and `captureException` (a no-op), for web and Jest. A `moduleNameMapper` in [../../package.json](../../package.json) points Jest at it, because jest-expo would otherwise resolve the `.native` file first and load the SDK in every suite that imports [errors.ts](errors.ts). Keep both files' exports identical. Suite: [__tests__/crashReporting.test.ts](__tests__/crashReporting.test.ts), which loads the `.native` file under a mocked SDK.
- [deviceSettings.ts](deviceSettings.ts) owns OS-settings deep links (battery optimisation exemption).
- [appUpdates.ts](appUpdates.ts) owns the version label settings shows (`appVersionLabel()`, `<version>-<n>` with `n` from `EXPO_PUBLIC_UPDATE_NUMBER`, see [../../scripts/publish-update.js](../../scripts/publish-update.js)) and the update helpers: `downloadNewUpdate()` returns the id of the update it downloaded, or null in development, with updates disabled or when nothing newer exists; `reloadIntoUpdate()` (never throws) serves the floating update banner and the tap handler; `isUpdateApplied({ updateId, updateCreatedAt })`, true when the running update is that update or a newer one (`Updates.createdAt` against the announced creation time), serves the tap handler and the scheduler's stale-notice check. expo-updates is already in the shipped binary, so all of it reaches installs over OTA.
- Service tests live in [__tests__/](__tests__/).

## Local Contracts

- Keep [NotificationScheduler.ts](NotificationScheduler.ts) and [NotificationScheduler.web.ts](NotificationScheduler.web.ts) API-compatible.
- Preserve notification identifiers as `${mitzvahId}__${YYYY-MM-DD}__${reminderIndex}` unless all scheduler, response, and tests are updated together. A notification not tied to a mitzvah (the pre-block notice, `blockNotice:<YYYY-MM-DD>`, the check-in reminders, `checkin:<YYYY-MM-DD>:<n>` with `data.blockId`, the update notice, `update:<update id>` with `data.updateId`, the hilula notices, `hilula:<hebrew abs day>:<before|evening>` with `data.hilula = { day, when }`, and the Rosh Chodesh notices, `roshChodesh:<hebrew abs day>:<before|evening|day>` with `data.roshChodesh = { day, when }`, and the weekly report notice, `report:<YYYY-MM-DD of the week's last day>` with `data.report = { week }`) uses an id without `__` and a `data.kind`, so `parseId` and every mitzvah lookup ignore it, and it carries no category (the taharah bedika reminders are the one exception, below).
- Android channels are `ANDROID_CHANNELS`, exported from both scheduler files. `ensureChannels()` in [notifications/os.ts](notifications/os.ts) creates all five (on a rebuild, a permission request and an update notice) and every candidate names one by `ChannelKey`, so a new kind of notification picks its channel in the same change:

  | id | name key | importance | lock screen | carries |
  | --- | --- | --- | --- | --- |
  | `default` | `notifications.channelName` | HIGH, vibration pattern, LED colour | PUBLIC | mitzvah reminders, the pre-block notice |
  | `hilulot` | `hilulot.title` | DEFAULT, no vibration pattern | PUBLIC | hilula notices |
  | `rosh-chodesh` | `roshChodesh.title` | DEFAULT, no vibration pattern | PUBLIC | Rosh Chodesh notices |
  | `taharah` | `taharah.home.title` | HIGH, no LED colour | PRIVATE | taharah reminders, the merged pre-block notification |
  | `system` | `notifications.channelSystem` | DEFAULT | system default | check-in reminders, the weekly report notice, the update notice |

  The mitzvot channel keeps the id `default`: a channel's sound and importance are the user's once it exists, and they follow the id.
- Check-in reminders come from `checkInFor()` in [../utils/checkIn.ts](../utils/checkIn.ts), for every block in the horizon and the three days before it, and are never scheduled for a finished check-in or one with nothing left to mark. They fire at the block's exit, two hours later, and as a last call at 20:00 on the location's clock the day after the block (half an hour before the next block's candle lighting when that evening is already holy), never at or after the check-in's deadline: the alot that ends the first weekday after the block, `checkInDeadline(block, location)`. `cancelCheckIn()` clears them from the tray and withdraws the rest through `rebuild()`, so a rebuild already in flight, which read the old state, is re-run instead of re-adding them. `settleCheckIn(date)` does the same after any mark or skip that leaves the day's check-in with nothing to mark; both are mirrored in the web shim. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` treat a settled check-in — finished, or nothing left to mark — like a done mitzvah.
- `MARK_DONE` must stay aligned with [../../scripts/withMitzvahNotificationAction.js](../../scripts/withMitzvahNotificationAction.js).
- Hilula notices exist only while `useUserStore.hilulotEnabled`. For each horizon day, `hilulaNoticesOn()` takes the Hebrew day whose daytime is that civil date (`civilHebrewDayAt()`, never the zmanim-driven `hebrewDayAt()`, which an Arctic winter shkia before noon pushed a day ahead) and fires at its shkia: `evening` for the hilulot of the next Hebrew day (it opens at this shkia) and `before` for those of the day after. Names join in the registry order, in the UI language. A notice whose shkia is past or inside a holy block is not scheduled; `hilulaLines()` names each one a block swallows, once per Hebrew day, in the pre-block notice: `holyBlock.notice.hilulaTonight` when the date opens on the erev, else `hilulaOn` with the weekday it opens. A change of `hilulotEnabled` rebuilds the schedule.
- Rosh Chodesh notices exist only while `useUserStore.roshChodeshEnabled`. For each horizon day, `roshChodeshNoticesOn()` takes the Hebrew day whose daytime is that civil date (`civilHebrewDayAt()`) and plans, on the `rosh-chodesh` channel: `before` at 20:00 on the location's clock when the Rosh Chodesh begins three Hebrew days later (`ROSH_CHODESH_BEFORE_DAYS`, `_BEFORE_HOUR`), `evening` at the day's shkia when it begins tonight, and `day` at 07:00 (`ROSH_CHODESH_DAY_HOUR`) on every Rosh Chodesh day. A two-day Rosh Chodesh begins on the 30th, so its lead notices count from day one and its `day` notice fires on both days; a month with no 30th before it has one day. The title names the new month (`roshChodeshLabel()`), and the body of a lead notice names the weekday of the evening the month enters. A notice whose time is past or strictly inside a holy block is not scheduled; `roshChodeshLines()` names each one the block swallows in the pre-block notice, once per month for the lead notices and once per day for `day`. A change of `roshChodeshEnabled` rebuilds the schedule.
- The weekly report notice exists only while `useUserStore.weeklyReportEnabled` (on by default). `planReport()` takes every block in the horizon and the three days before it whose `weekEndFor()` is not null (it holds a Saturday: motzaei Shabbat, or a Yom Tov that follows Shabbat, whose last day is then the week end; a mid-week Yom Tov has none) and schedules `report:<week end>` on the `system` channel at the block's exit plus `REPORT_DELAY_MIN` (45) minutes, after the check-in's first nudge (at the exit) and before its second (two hours on). The payload is `data.report = { week }`, the week end's date key; no category. A trigger that is past or strictly inside another block is not scheduled, and a rebuild during the 45 minutes still plans it. A change of `weeklyReportEnabled` rebuilds the schedule.
- Taharah reminders exist only while `useUserStore.taharahEnabled`. `planTaharah()` maps each horizon day's `taharahTasksFor()` tasks to `data.kind = 'taharah'` notifications, `data.taharah = { task, day, onah? }` with `day` the Hebrew abs: `hefsek` at the task's end minus `hefsekLeadMin`; `bedikaMorning` at sunrise plus 30 minutes and `bedikaEvening` at its end minus `bedikaEveningLeadMin`, both skipped once marked; `tevilaPrep` at the tevila task's start minus `tevilaPrepLeadMin` plus `tevila` at that start (tzeit, or the block's exit on motzaei Shabbat / Yom Tov, from `HebcalService.nightfall()`); `perisha` at the onah's start; `bedikaVeset` an hour before the onah ends, only when it is required (the onah beinonit is among its reasons); `expectOnset` at 10:00 on the location's clock; and, for a woman only, `postBlock` 15 minutes after a holy block that left a clean day's bedika slot unmarked. Ids carry no `__`: `taharah:<task>:<day>`, `taharah:<task>:<day>:<night|day>` for `perisha` and `bedikaVeset`, `taharah:postBlock:<YYYY-MM-DD>`, `taharah:preBlock:<YYYY-MM-DD>` (the merge below); a repeated id keeps the first.
- With `discreetNotifications` (the default) every taharah notification shows only the neutral `taharah.notify.discreet*` text; otherwise it reads `taharah.notify.title.<task>` / `body.<task>`, with the disputed line when the onah is in dispute.
- `beforeQuiet()` is the one rule for taharah triggers: a trigger strictly inside a holy block goes out ten minutes before the block's candle lighting instead, unless the task's own window (`TaharahDraft.end`) outlasts the block, when it waits for the block's end (a perisha night opening at motzaei Shabbat's shkia fires at the exit); a trigger not after now is dropped. A `tevila` whose own trigger is inside a block is replaced by its `tevilaPrep` alone, worded by `tevilaPrepShabbat` and naming candle lighting; the reminder for the later night still fires at the block's end.
- Drafts that `beforeQuiet()` pulled ahead of a block are grouped by the block they were moved out of, `quietBlockAt(draft.trigger).days[0]`; unshifted and deferred drafts are scheduled one by one. Every group, a lone draft included (its own text would name a deadline inside the block), becomes ONE notification: `taharah:preBlock:<first day of the block>`, `data.taharah = { task: 'preBlock', day }` with `day` the Hebrew abs of the block's first day (`firstDayAbs()`, shared with `postBlock`), no category, at the shifted instant. Discreet it reads `discreetTitle` / `discreet.preBlock`; otherwise `title.preBlock` with the block's `checkin.in.*` phrase, and a body of each member's own non-discreet title in the order the originals were due, repeated titles once, plus `taharah.disputed` once if any member is disputed. The members' own bodies (`tevilaPrepShabbat` included) are dropped in the merge.
- Only `bedikaMorning` and `bedikaEvening` carry the `taharah_bedika` category, one `MARK_DONE` button titled `taharah.notify.markDone`; no other taharah reminder has a category, so a hefsek or an immersion is only ever entered in the app. `markDoneFromNotificationData()` handles that button before any mitzvah lookup, in the headless action task too, by recording a clean `bedika` event for the slot, unless the slot already has a result, and dismisses the notification.
- `taharahNotificationSettled(data)` replays `deriveCycle()` over the store's events at the moment of asking: a bedika is settled when its clean day has no such slot left or the slot has a result, a `hefsek` once the cycle is past the hefsek stage, a `tevila` / `tevilaPrep` once the stage is `tahor`, a `postBlock` once no clean day in that block lacks a slot, an `expectOnset` once the latest onset is on or after its day; `perisha`, `bedikaVeset` and `preBlock` never. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` use it.
- `initNotificationHandlers()` also rebuilds on a `useTaharahStore` change of events, settings, the discreet switch or any lead, while `taharahEnabled` is on, and on a change of `taharahEnabled` itself.
- The daily rebuild is an `expo-background-task` task named `jew-in-time-daily-rebuild-v2` (`DAILY_REBUILD_TASK` in [notifications/ids.ts](notifications/ids.ts)), registered with `minimumInterval: 60` (minutes; the OS decides the real cadence, 15 at the least). Its body returns `BackgroundTaskResult.Success` or `.Failed`. `registerDailyRebuildTask()` first unregisters `LEGACY_DAILY_REBUILD_TASK` (`jew-in-time-daily-rebuild`), the registration an `expo-background-fetch` build leaves on an updated install; a failing cleanup never blocks the registration. The web shim keeps the v2 name. The notification action task is unchanged and keeps its own result codes (`BACKGROUND_NOTIFICATION_RESULT`).
- `notifyIfUpdateReady(now)` runs at the end of every `DAILY_REBUILD_TASK` run (a failed check is logged with `console.warn` and never fails the task): it downloads a newer update through `downloadNewUpdate()` and presents one notice per update id, remembered under `UPDATE_NOTIFIED_KEY` only after the notice is scheduled, and withdraws the previously remembered notice first, so the tray holds one update notice at most and a run skipped for a holy block (`isQuietAt()` once onboarded), a switched-off notifications setting or a denied permission (`hasNotificationPermission()`) retries next hour. Title `update.notice.title`, body `home.updateReady`, Android on the `system` channel, immediate trigger. A notice carries `data.updateId` and `data.updateCreatedAt`; one whose update, or a newer one, is already running (`isUpdateApplied()`) is stale: `shouldSuppressForCompletion()` hides it and `dismissCompletedPresentedNotifications()` clears it from the tray at the next launch. `SCHEDULE_FORMAT` is unchanged: the notice is presented, never left pending.
- A reminder gets the `mitzvah_reminder_text` category (`OPEN_TEXT` + `MARK_DONE`) exactly when `hasSiddurText()` is true for its window date and its trigger is not a holy block's opening edge (`opensQuietBlock()`); otherwise `mitzvah_reminder`. `OPEN_TEXT` opens the app to the reader and needs no native handling; the Android plugin only dismisses on `MARK_DONE`. The same decision is the payload's `data.hasText` (true exactly when the text category is chosen), which routes the body tap.
- Category button titles are translated, so a language change rebuilds; it is part of the user-store subscription.
- Raise `SCHEDULE_FORMAT` whenever the shape of a scheduled notification changes (category, actions, payload). A rebuild deletes the stamp before it touches the schedule and writes it back when done, and a foreground with a missing or stale stamp rebuilds once — so an update, or a rebuild cut short by a reload (a language switch reloads the app for RTL), is redone; otherwise reminders already scheduled by the previous bundle keep the old shape until the next day. It is raised too when a mitzvah leaves the registry (`tzitzit`, 2026-10-11), so the `<id>__…` reminders already scheduled for it are cleared on the first foreground.
- `cancelForMitzvah(id, date)` must cancel all pending reminders for that mitzvah/date and dismiss the ones already in the tray; every done and skip path relies on it.
- Always pass `Location` to `HebcalService.isShabbat(date, location)` when halachic boundary behavior matters.
- Holy blocks: `holyBlockAt(instant)` returns the block whose [candle lighting, exit] span contains the instant, edges included, the exit being `holyBlockExit()` of the last day (tzeit itself is still inside); `isHolyDay(date)` and `holyBlockOn(date)` are day-granular, judging the location's calendar date of `date` by its daytime. A block merges every touching Shabbat / Yom Tov / Yom Kippur day. Per-day holiday flags are memoized per Hebrew day and `inIsrael`.
- `isShabbat` and `isYomTov` both derive from one internal `hebrewDaysAt(instant, loc)` primitive. Its civil day is the instant's date in the LOCATION's zone, the same day `ZmanimService` resolves, never the device's. A Hebrew day turns over at shkia, and between shkia and tzeit both candidate days are returned so an observance counts if either carries it. Do not reintroduce a Gregorian-day check for either. The exit margin does not move the Hebrew date: at tzeit plus five minutes on motzaei Shabbat the date is Sunday while `holyBlockAt()` still answers the block, and no window starts in that gap because the night windows of a block's last day open at `nightfall()`.
- Use `getHebrewDateAt(instant, loc)` for "today" displays (it advances at shkia) and `getHebrewDate(date)` only for calendar grids, where each cell is a civil day. `hebrewDayAt(instant, loc)` is the same day as an `HDate`, for a text that resolves "now": from shkia on, bein hashmashot included, it is the next day. `hebrewNightAt(instant, loc)` is the Hebrew day whose night is in effect or comes next, for a text said at night: before dawn (alot hashachar) the night still running, from dawn on tonight's. Dawn is `dawnAt(instant, loc)`, the alot of the location's calendar date of `instant`, or 04:00 on the location's clock (`DAWN_FALLBACK_HOUR`) where the sun neither rises nor sets: the one home of that boundary, which the app's day (`appDay()` in [../utils/locationDay.ts](../utils/locationDay.ts)) and Chok LeYisrael's learning day also turn at.
- Avoid UTC date shortcuts for mitzvah logic.
- `Zmanim.chatzotLayla` is chatzot halayla (solar midnight) for the night FOLLOWING that day, so it falls on the next civil date. It is the correct end for night windows.
- Battery-optimisation exemption is the user's half of reliable delivery; route it through `openBatteryOptimizationSettings()` and never request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, which Google Play restricts to a narrow set of app categories.
- Exact-alarm delivery depends on the Android manifest, not on any runtime call; see the root AGENTS.md notification section before touching `android.permissions` or the config plugins.
- `ZmanimService` resolves the calendar day in the LOCATION's zone (`setDate` with a zoned Luxon DateTime, cache keyed on that ISO date). Never hand it a bare `Date`. It overrides the GeoLocation's `getAntimeridianAdjustment()` with `antimeridianAdjustment(loc)`, the same 20-hour check computed from the zone's true standard offset: kosher-zmanim 0.9.0 (the latest) flips the sign of the raw offset for every zone that keeps DST, which rolled Sydney, New Zealand and the Aleutians a day forward. Nothing else the app calls reads that offset. Pinned by the day-resolution tests in [__tests__/ZmanimService.test.ts](__tests__/ZmanimService.test.ts); recheck after a kosher-zmanim upgrade.
- `initNotificationHandlers()` returns a teardown; the caller must run it on unmount, or store subscriptions stack up and one change fans out N rebuilds.
- `withLock()` coalesces on the trailing edge: a request arriving mid-run queues exactly one re-run. Never make it drop-on-conflict.
- Only `rebuildForNewDay()` stamps `LAST_REBUILD_KEY`; a settings-driven `rebuild()` must not, or it suppresses that night's recovery run.
- Scheduling is capped and ordered by trigger time in `buildPlan()` (`IOS_MAX - IOS_HEADROOM` on iOS, `PENDING_LIMIT` elsewhere), every candidate names its channel and `os.schedule()` puts that `channelId` on the trigger, and a trigger outside its own window is dropped.
- [notifications/](notifications/AGENTS.md) holds the planning contract: planners are pure over a `PlanInput` read once by `readPlanInput()`, only [notifications/os.ts](notifications/os.ts) calls expo-notifications for scheduling, and the facade keeps every exported name, the `NotificationScheduler` method set and the module-scope `defineTask` calls. Internal calls go through `NotificationScheduler.<method>` so the suites' spies keep working.
- Whether a reminder fires is `reminderFires()` from [../utils/skipRules.ts](../utils/skipRules.ts): ahead, inside its own window, and not strictly inside a holy block. The plan and the mitzvah screen's next-reminder preview both reach it through `windowTriggers()` in [notifications/planners/mitzvot.ts](notifications/planners/mitzvot.ts), the one per-window rule, so the preview is `nextReminderAt()`, exported by the facade: the first trigger the scheduler would fire, across windows, never a copy of its filter. The horizon steps by the location's calendar dates through any block that is reached or starts the next day, to the first weekday after it, and mitzvah reminders are also planned for the day before it, for a window still open after midnight; each step is the device-local midnight of that date, with zmanim at the location's noon, the mapping every day-level surface uses.
- [notificationResponseHandler.ts](notificationResponseHandler.ts) opens nothing while the app is quiet (onboarded and `isQuietAt()` now), drops a buffered cold-start tap then too, routes the body tap of a mitzvah reminder to the reader (`/siddur/[id]` with the notification's `date`) when `data.hasText` is true and to the detail screen (`/mitzvah/[id]`) otherwise or when the date cannot be recovered, the pre-block notice to home, a check-in reminder to `/checkin`, a taharah reminder to `/taharah`, a hilula notice to `/hilulot`, a Rosh Chodesh notice to `/rosh-chodesh` and a weekly report notice to `/report` with its `week`, and reloads into the update for an update notice through `reloadIntoUpdate()`, or opens home when that update, or a newer one, is already running. `MARK_DONE` is never blocked.
- `AppResetService` wraps its work in `setSchedulingSuspended(true)` so resetting the stores cannot re-arm a schedule from the restored defaults. It resets `useTaharahStore` with the other stores and, after the main MMKV wipe, calls `clearTaharahStorage()`.
- The taharah instance (`jew-in-time-taharah`) is encrypted with a 16-character key held in `expo-secure-store` under `taharah-mmkv-key`, read synchronously at module load and made on first use from `expo-crypto` random bytes. The key is always stored with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`: it never travels in a backup or device transfer, yet the nightly rebuild and a lock-screen mark-done still read it on a locked phone. A key made just now clears the file it opens, since it cannot open anything older.
- When no key is available (web, or a keychain that cannot be read, such as a launch while the device is locked) the module opens a different, unencrypted file (`jew-in-time-taharah-unencrypted`). It must never open the encrypted file without its key: that decodes ciphertext as data and corrupts it.
- `clearTaharahStorage()` wipes the data and replaces the key in the secure store and in the running instance (`recrypt`). Deleting the key instead would leave this process writing under a key the next launch no longer finds. It never throws and restores the previous stored key if the new one cannot be applied. Run without a readable key, it wipes only the fallback file and sets `taharah:wipe-pending` in the plain store (after the reset's own wipe of it); the next launch that can read the key ignores the stored one, makes a new key and starts the encrypted file clean, then clears the flag.
- `ZmanimService.getZmanim()` must never throw. It returns `Zmanim | null`, where `null` means the sun neither rises nor sets that day; every caller must handle `null` instead of assuming a value. Depression-angle zmanim that have no solution fall back to their fixed-minute shita (alot 72 min, misheyakir 52 min before sunrise), and misheyakir is always kept inside `(alot, netz)`.
- A planner failure must cost only its own candidates (each mitzvah and day, each block, and the weekly report, taharah, hilula and Rosh Chodesh planners as a whole), so one failing mitzvah cannot empty the whole schedule: `cancelAll()` has already run.
- `skipOn` decisions come from `isSkippedAt()` in [../utils/skipRules.ts](../utils/skipRules.ts), evaluated at the computed window's `start`. Do not add a local copy of that predicate here, and do not judge the skip from `fromDate` — that instant carries the rebuild's clock time.
- `expo-file-system` (read by `SiddurService`) and `expo-keep-awake` (used by the reader) are pinned to the versions already linked into the shipped binary. Raising either is a native change and needs a build.
- `TaskManager.defineTask` calls stay at [NotificationScheduler.ts](NotificationScheduler.ts) module scope, and that module stays imported from the root [../../index.js](../../index.js) entry so both background tasks are defined during headless launches (killed-state `MARK_DONE` taps, background tasks). Route-only imports do not reach headless mode. Pinned by [backgroundTaskEntry.test.ts](__tests__/backgroundTaskEntry.test.ts), which also pins that `crashReporting` is imported before `expo-router/entry` and before `NotificationScheduler`.
